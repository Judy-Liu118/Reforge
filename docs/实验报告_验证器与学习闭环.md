# 实验报告：静默错误的验证器，以及它能否驱动"从失败中学习"

> 2026-10。分支 `exp/verifier-ladder`。全部是实验代码（`scripts/`），不改生产链路。
> 文中每个数字都出自本地结果文件，可用文末"复现"一节的脚本重新算出。

## 摘要

Reforge 是一个 agent 执行可靠性 runtime。它现有的启发式评估器对一类错误看不见：程序 exit 0、不报错、打印一个貌似合理但错误的数。本文称之为**静默错误**。

围绕它做了两个实验，结论如下：

1. **谁能判静默错。** 便宜的非 LLM 检查在"照着已知错误写规则"的同分布数据上召回很高（0.84–0.98），换成没见过的错误类型就掉到 11%–14%（n=28），在合法但长得像脏数据的表上误报 18/18。LLM critic 在同一批没见过的错误上召回 28/28，诱误报 0/18。
2. **在真实公开数据上判得准不准。** InfiAgent-DABench 95 题：critic 在 agent 做对的运行上误报 5/77 = 6.5%（95% CI [2.8%, 14.3%]），在做错的运行上召回 11/18 = 61%（[39%, 80%]）。人工核对其中 2 条"误报"，发现都是 agent 代码确有缺陷、基准答案没查出来。
3. **判官能不能驱动学习。** 把"裁判准不准"和"反馈有没有点出错因"拆成两个因子后：反馈带诊断使做对率提高 0.33（[+0.17, +0.50]，14 张表）；裁判从完美的 gold 换成会判错的 critic，代价是 0.07（[−0.06, +0.21]），区间跨零，**在这个样本量下未测出**。

一句话：LLM 验证器的价值有两份，一份是当闸门拦住错误，另一份是生成"错在哪"的诊断。在本实验里，驱动学习的主要是后者。

所有结论都受小样本限制，第 5 节逐条列出。

## 1. 背景与动机

### 1.1 静默错误是什么

Reforge 的执行循环是：规划 → 生成一份脚本 → 执行 → 评估 → 失败则反思重试。评估器靠退出码、异常、输出形态等启发式信号判断成败。

这套机制对**崩溃**有效：报错信息会暴露问题，模型看着 traceback 通常能自己修好。但对下面这种情况无效：

```python
df = pd.read_csv("expenses.csv")
print(df["cost"].sum())      # 文件最后一行是 TOTAL 汇总行，结果约为真值的两倍
```

程序正常结束，打印了一个数，数的量级也合理。没有任何信号告诉评估器它是错的。

### 1.2 崩溃可恢复 vs 静默

这个区分贯穿全文，值得先说清：

| | 崩溃 | 静默错误 |
|---|---|---|
| 表现 | 抛异常、exit ≠ 0 | exit 0，打印错数 |
| 评估器 | 能看见 | 看不见 |
| 重试循环 | 会触发，报错信息指向修法 | 不触发 |
| 记忆能帮上的地方 | 重试时给修复提示 | 只有规划阶段，动手之前 |

上一轮实验（蒸馏策略卡消融）已经量过：在 542 条静默陷阱运行里，线上启发式评估的召回是 1/346。它不是调参能修的，是结构性的失明。

### 1.3 由此引出的三个问题

1. 谁能判静默错？便宜的规则够不够，什么时候必须上 LLM？
2. 判得准不准？特别是在真实数据上会不会乱报警？
3. 如果判官不完美，还能不能用它驱动"失败 → 提炼教训 → 下次做对"的学习闭环？

实验一回答前两个，实验二回答第三个。

## 2. 方法总览

### 2.1 四层验证器

按成本从低到高分四层，每层独立评估：

| 层 | 做法 | 用不用 LLM | 看什么 |
|---|---|---|---|
| L0 启发式 | 线上现有评估器的判定 | 否 | 退出码、异常、输出形态 |
| L1 静态探针 | 先给数据做画像找"危险信号"（汇总行、哨兵值、重复行、键格式不一致等 9 种），再用正则检查代码有没有处理 | 否 | 数据 + 代码文本 |
| L1b 变形复跑 | 把探针发现的信号在数据副本上修掉，重跑同一份代码。输出变了，说明原结果依赖脏数据 | 否 | 数据 + 代码的实际行为 |
| L2 critic | 把任务、数据画像、代码、输出交给一个 LLM，用对抗式提示让它找错。输出 `wrong` / `ok` / `abstain` 三选一，并写出疑点和依据 | 是 | 以上全部 |

L1 和 L1b 的共同前提是"探针认得这种脏"。探针是照着已知错误类型写的。

### 2.2 两条纪律

**gold 只当尺子。** 每道题都有确定性的正确答案（gold）。它只用来给最终结果打分，不进入被测对象。验证器看不到 gold；实验二里 critic 判官那条臂的整个循环也看不到 gold。

**验证器冻结。** 第一轮测量结束后，验证器文件 `scripts/run_verifier_ladder.py` 的 sha256 前 16 位固定为 `ce417eedcde2de3d`，之后所有实验的每条输出记录都盖这个哈希。后续测试集无论结果多难看，都不许回头改验证器。唯一从外部调过的是 critic 的总 token 预算上限，它决定能评多少题，不影响对单题的判定。

> 关于哈希的一个注意点：`ce417eedcde2de3d` 是实验机器上工作副本（CRLF 换行）的哈希。Git 入库时换行被规范化为 LF，同一份文件在仓库里的哈希是 `9c330818e23e6588`。两者内容逐行相同，只差换行符；在 LF 环境检出后重算会得到后一个值。

### 2.3 模型

| 角色 | 模型 |
|---|---|
| critic | qwen3.8-max（第一轮与留出测试）、qwen3.8-max-0902（InfiAgent 与实验二） |
| agent | qwen3.8-27b（留出测试）、qwen3.8-2.4t-a95b 限思考 4000 token（InfiAgent 与实验二） |
| 蒸馏器（实验二） | deepseek-v4-pro |

agent 在这些实验里只负责"制造待验证的运行"，不是被测对象。

## 3. 实验一：验证器刻画与真实数据精确率

### 3.1 起点：同分布上的测量

数据是上一轮消融留下的 542 条运行日志（346 条错、196 条对），来自 10 对合成的静默陷阱任务。不重跑 agent，只回放日志。

| 层 | 召回 | 精确率 | LLM token / 条 |
|---|---|---|---|
| L0 启发式 | 0.003（1/346） | 0.333（1/3） | 0 |
| L1 静态探针 | 0.838（290/346） | 0.990（290/293） | 0 |
| L1b 变形复跑 | 0.983（340/346） | 0.994（340/342） | 0 |
| L2 critic 单独 | 0.873（302/346） | 0.984（302/307） | 382 |
| L1 → critic（只审 L1 放过的） | 0.983（340/346） | 0.977（340/348） | 253 |

看上去结论是"便宜层吃掉了绝大部分，LLM 只是补缺"。**但这个结论有个明显的漏洞**：探针就是照着这 10 种陷阱写的，这是同分布上界，不是泛化能力。而且语料里没有"数据长得可疑但其实合法"的对照，精确率等于没测。

另一个值得记的细节：critic 在哨兵值类错误（用 −1 表示缺失，被直接算进均值）上只抓到 11/55。它的疑点里写着"−1 可能是无效值"，但多数时候选择弃权或放行，因为 −1 作为数值本身合法。

> **小结**：同分布上便宜层很强，但这个数不能外推。需要留出测试。

### 3.2 留出测试：没见过的错 + 诱误报

验证器冻结后，新造两组数据，agent 重新跑（57 条运行）：

- **没见过的污染（13 种）**：空格千分位、撇号千分位、货币前缀、百分号、括号负数、`万` 后缀、999 哨兵等。都是真实存在的脏数据形态，但探针没有针对它们的规则。
- **诱误报（6 种）**：数据合法，但长得像脏数据。比如真实的 −1℃ 气温、合法的重复销售记录、一家名叫 "Total" 的公司、本来就该内关联的两张表。正确做法是**不要**"修"。

| | 没见过的污染：召回（agent 做错 28 条） | 诱误报：误报（agent 全做对 18 条） |
|---|---|---|
| L1 静态探针 | 4/28 = 14% [6%, 32%] | 18/18 = 100% [82%, 100%] |
| L1b 变形复跑 | 3/28 = 11% [4%, 27%] | 18/18 = 100% [82%, 100%] |
| L2 critic | 28/28 = 100% [88%, 100%] | 0/18 = 0% [0%, 18%] |

方括号内是 Wilson 95% 置信区间，下同。在没见过的污染里 agent 做对的 11 条上，critic 误报 0/11，静态探针 2/11。

**为什么便宜层不泛化。** 两个方向都是同一个原因：探针只认形状，不懂含义。

- 认不出新形状：规则里有逗号千分位，没有空格千分位，后者就是盲区。
- 分不清形状相同但含义不同的情况：−1 在"年龄"列是哨兵，在"气温"列是真实读数。探针只看到"正数列里出现了 −1"。变形复跑更直接：把 −1 "修"掉重跑，输出当然变了，于是报错。

critic 能做对，是因为它读了任务描述和列名，知道气温可以是负的。

> **小结**：便宜层是"已知错误类型的回归测试"，不是通用判官。泛化到新错误类型和区分合法数据，在这组测试里只有 LLM 做到了。样本是 28 条和 18 条，区间如表中所示。

### 3.3 真实数据：InfiAgent-DABench

前两组数据都是自己造的。第三组用公开基准 InfiAgent-DABench 的验证集，表是真实的公开数据，题和答案由基准提供。

- **子集**：答案标签为单个数值的题，共 95 题、42 张表。这样对错判定没有歧义。
- **跑法**：四层各自独立评全部 95 条，critic 无条件全判，不做级联。
- **主测指标**：agent 做对的运行上，每层误报多少。真实数据里脏数据不多，这里主要看"会不会乱报警"。

agent 做对 77 题，做错 18 题。

| 层 | 误报率（做对的 77 条） | 召回（做错的 18 条） |
|---|---|---|
| L0 启发式 | 0/77 = 0% [0%, 4.8%] | 0/18 = 0% [0%, 17.6%] |
| L1 静态探针 | 10/77 = 13.0% [7.2%, 22.3%] | 1/18 = 5.6% [1.0%, 25.8%] |
| L1b 变形复跑 | 5/77 = 6.5% [2.8%, 14.3%] | 0/18 = 0% [0%, 17.6%] |
| L2 critic | 5/77 = 6.5% [2.8%, 14.3%] | 11/18 = 61.1% [38.6%, 79.7%] |

几点说明：

- 静态探针的 10 条误报里，6 条是"有重复行"、4 条是"分组键有大小写变体"。真实表里这些现象常见且多数无害。
- 做错的 18 条里有 6 条是 agent 根本没按格式输出答案，这类不是"算错了数"，验证器抓不到很正常。
- 召回的分母只有 18，区间很宽。它是副产品，不是这个实验的主测目标。
- critic 共 95 次调用、58.5 万 token、0 次报错，平均每次约 6 千 token。真实表的画像比合成表长得多。

### 3.4 人工核对：critic 的 5 条"误报"

critic 的 5 条误报是 da0129、da0372、da0007、da0468、da0039。逐条看：

| 题 | critic 的理由 | 核对结果 |
|---|---|---|
| da0129、da0372 | 输出格式不符（如要求两位小数，打印了 32.2） | 数值正确，属于挑格式。算误报 |
| da0007 | 质疑表里的占位行 | 不影响答案。算误报 |
| **da0468** | 代码选错了分类列，过滤出 0 行 | **critic 说对了** |
| **da0039** | 列里有 0，直接取对数得负无穷 | **critic 说对了** |

后两条我重跑了 agent 的代码：

- **da0468**：题目问某类罪犯年龄分布里的离群值个数，gold 是 0。agent 的代码在循环里把分类列覆盖成了错的那一列，过滤后是 0 行，分位数全是 NaN，离群值个数自然是 0。用正确的列（681 行）重算，离群值也是 0。也就是说 agent 在空数据上得到了一个恰好正确的数。
- **da0039**：题目要求三个输出（正态性检验的 p 值、对数变换后的均值、标准差）。agent 的均值打印出 `-inf`、标准差是 `nan`。但基准的标签文件里只有 p 值一项，另外两项没被校验，所以判对。

这给出两个口径，都应该报：

| 口径 | critic 误报率 | critic 召回 |
|---|---|---|
| 按基准 gold | 5/77 = 6.5% [2.8%, 14.3%] | 11/18 = 61.1% [38.6%, 79.7%] |
| 人工核对后（这 2 条改标为"agent 实际有错"） | 3/75 = 4.0% [1.4%, 11.1%] | 13/20 = 65.0% [43.3%, 81.9%] |

**关于第二个口径的诚实说明**：这是看过结果之后做的人工改标，而且只核对了被 critic 标记的 5 条。另外 72 条"做对且 critic 没报"的运行没有做同样的检查，里面也可能藏着碰巧答对的。所以第二个口径是有偏的，只能当参考。

**为什么"与 gold 不一致 ≠ 判官错"。** 基准的 gold 检查的是最终答案，critic 检查的是得出答案的过程。过程错而答案碰巧对（da0468）、或者答案的一部分没被校验（da0039），两者就会分歧，而这时对的是 critic。用"答案与 gold 一致"来定义"运行正确"，在真实数据上本身就带噪声。

> **小结**：在真实公开数据上，critic 的误报率点估计 6.5%，区间上限 14%。它是四层里唯一有实质召回的。便宜层在真实数据上既抓不到错，静态探针还有 13% 的误报。

## 4. 实验二：学习闭环 · 四臂

### 4.1 问题

Reforge 的记忆机制设想是：agent 在一道题上失败 → 把这次经历蒸馏成一张去具体化的策略卡 → 下次遇到同类题时注入规划阶段。

上一轮消融已经测出这条路在同类任务间有效，但当时"这次是对是错"由 gold 告诉蒸馏器。生产环境里没有 gold。如果换成会判错的 critic 来告诉，提升还剩多少？

### 4.2 为什么是四臂

最初的设计是三臂：cold（无记忆）、warm-gold（gold 判成败）、warm-critic（critic 判成败）。冒烟时出现了一个反直觉的结果：critic 臂比 gold 臂好。

原因在于两条臂之间**同时变了两件事**：

- 谁判成败：gold 永远对，critic 会错。
- 蒸馏器拿到什么反馈：gold 只能说"你打印了 X，正确值是 Y"；critic 会说"bmi 列里的 −1 是缺失占位值，被直接算进了均值"。

蒸馏器看不到数据。只给它一个正确值，它猜不出错因，蒸出来的是"聚合前先检查数据分布"这类泛泛的卡。critic 看过数据画像，它的疑点直接点名了坑。

于是加了第四条臂把两个因子拆开：

| 臂 | 谁判成败（决定卡的极性） | 蒸馏器拿到的反馈 |
|---|---|---|
| cold | — | 无记忆 |
| warm-gold（贫） | gold | 只有"打印值 / 正确值" |
| warm-critic | critic | critic 的疑点和依据 |
| warm-gold+诊断 | gold | **同一段** critic 疑点和依据 |

由此得到两个干净的对比：

- **诊断价值** =（warm-gold+诊断）−（warm-gold 贫）。裁判相同，只差反馈。
- **裁判噪声代价** =（warm-gold+诊断）−（warm-critic）。反馈文本逐字相同，只差谁定极性。

### 4.3 数据与流程

**数据**：InfiAgent 的真实表，往副本里注入数据质量文献里的标准错误类型。原始表只读，注脏副本写到独立目录，gold 从干净版算。

**准入标准**（都满足才进全量）：

1. 参考的朴素解法不抛异常，且结果偏离 gold 超过 5%；参考的正确解法精确等于 gold。
2. agent 冷跑一次：不抛异常、一次尝试就出错数。这次准入冷跑单独记录，**不进分析**，避免"用同一批数据既筛题又算提升"。

最终存活 7 种坑，每种 2 张真实表，共 14 张注脏表：footer 汇总行、完全重复行、−1 哨兵、分组键大小写/空格变体、同义异写（如 `S` / `Southampton`）、关联键不一致、一对多关联放大。

**被丢弃的坑**：

| 坑 | 丢弃原因 |
|---|---|
| 千分位逗号、单位后缀、欧式小数逗号 | 列被读成字符串，第一次尝试就抛异常，报错信息等于提示。这是崩溃恢复，不是静默 |
| groupby 丢 NaN 组、内关联丢行 | 能让它咬住的题面太人工（"打印所有分组小计之和"） |
| 同义异写的一张表 | agent 自己把题面里的小写值改成了首字母大写，在干净表上也会答错，与坑无关。换了另一张表 |

**流程**（每轮，任务顺序打乱，四臂共用同一顺序，共 3 轮）：

1. 每张表空记忆跑一次，即 cold 臂。同一次运行兼作同坑另一张表的种子。
2. 种子运行分别交给 gold 和 critic 判，按上表蒸出三张卡。critic 弃权则不蒸卡。
3. 每张表各带一张卡再跑三次，即三条 warm 臂。种子和目标永远是同一种坑、不同的真实表。
4. 所有运行一律按 gold 打分。

agent 的输入只有一句任务文本，例如"读取 insurance.csv，计算 bmi 列的平均值，打印最终结果（保留两位小数）"。不给表头、不给样本行。循环是"失败才重试"，最多 3 次，四臂一致。

### 4.4 结果

168 次运行，0 次报错。

**四臂做对率**

| 臂 | 做对 |
|---|---|
| cold | 0/42 = 0.0% |
| warm-gold（贫） | 19/42 = 45.2% |
| warm-critic | 30/42 = 71.4% |
| warm-gold+诊断 | 33/42 = 78.6% |

**配对对比**（配对单位是表，每张表取 3 轮均值，n=14，t 分布 95% CI）

| 对比 | 差值 | 95% CI |
|---|---|---|
| warm-gold（贫）− cold | +0.452 | [+0.207, +0.698] |
| warm-critic − cold | +0.714 | [+0.490, +0.939] |
| warm-gold+诊断 − cold | +0.786 | [+0.624, +0.948] |
| **诊断价值** | **+0.333** | [+0.165, +0.502] |
| **裁判噪声代价** | **+0.071** | [−0.063, +0.206] |

**按坑分面**（做对 / 运行数）

| 坑 | cold | gold（贫） | critic | gold+诊断 |
|---|---|---|---|---|
| 键大小写/空格变体 | 0/6 | 6/6 | 6/6 | 6/6 |
| 一对多关联放大 | 0/6 | 6/6 | 6/6 | 6/6 |
| 关联键不一致 | 0/6 | 4/6 | 6/6 | 6/6 |
| −1 哨兵 | 0/6 | 2/6 | 5/6 | 5/6 |
| footer 汇总行 | 0/6 | 0/6 | 5/6 | 4/6 |
| 完全重复行 | 0/6 | 1/6 | 1/6 | 4/6 |
| 同义异写 | 0/6 | 0/6 | 1/6 | 2/6 |

诊断的价值集中在 footer 和哨兵：只知道正确值时蒸馏器猜不出错因，知道了就基本能修。键变体和关联放大三条 warm 臂都满分，贫反馈也够用。

### 4.5 critic 判错了哪些种子

42 次种子运行按 gold 全是错的。critic 判"错"36 次、判"ok"6 次、弃权 0 次。

这 6 次需要拆开看。cold 运行每轮打印同一个错值，critic 按打印值去重后**实际只调用了 14 次，每张表一次**。所以 6 张反极性卡对应的是 2 个独立判定，各自在 3 轮里重复：

| 种子表 | critic 的疑点原文 | 判定 |
|---|---|---|
| 重复行 · `Credit.csv` | "最可能的错因是存在 48 行完全重复，若任务本意是统计唯一记录则总和会被重复计入" | ok |
| 同义异写 · `hotel_data.csv` | "若把 New York City 理解为纽约市而非精确字符串，代码会漏掉 city_name 为 'NYC' 和 'New York' 的记录" | ok |

两条都是 critic **看见了问题，但认为题意有歧义，判了 ok**。这和实验一里它在哨兵值上的保守倾向一致。

后果：

- 这 2 个种子的下游运行里，warm-critic 0/6，warm-gold+诊断 2/6。
- 判 ok 就蒸成"成功经验"卡。其中一张明确写了"任务未要求去重，则不额外做唯一性处理"，是一张教反了的卡。
- 其余 12 个种子上两臂几乎一样：warm-critic 30/36，warm-gold+诊断 31/36。裁判噪声代价基本全部来自这 2 张表。

### 4.6 warm 运行为什么还会失败

三条 warm 臂共 44 次失败。按关键词粗分（不是人工逐条核对，只看量级）：

| 类别 | gold（贫） | critic | gold+诊断 |
|---|---|---|---|
| 卡没点到错因 | 5 | 0 | 0 |
| 卡点到了，计划没采纳 | 3 | 3 | 0 |
| 计划有，代码没做 | 4 | 0 | 1 |
| 代码做了检查，结果仍错 | 11 | 9 | 8 |
| 合计 | 23 | 12 | 9 |

"卡没点到错因"只出现在贫反馈臂，与 4.2 的解释一致。

最大的一类是"做了检查，结果仍错"。抽看的几条机制相同：**agent 在脚本里把异常打印了出来，但脚本已经写完，没法根据打印结果改。**

- 同义异写 · titanic：输出里打印了 `S 419 / SOUTHAMPTON 225`，下一行照旧只筛 `S`。
- footer · insurance：打印了最大值 17,755,824（正是那个汇总行），但过滤条件是"转不成数字的行"，汇总行是数字。
- 重复行 · hotel：打印了"完全重复行 127"，随后的注释是"按要求对全部原始行求和"。

这是"盲写一份脚本、失败才重试"这种循环的直接后果，也解释了同义异写为什么三条臂都几乎不动：这个坑必须先看到实际取值，才知道该把什么合并。

另外，失败的运行里有 11 条用了 `dtype == object` 这种在 pandas 3 下不再成立的老写法，其中 10 条在贫反馈臂。它们是否是失败主因没有逐条确认。真正抛过异常的只有 1 条。

### 4.7 结论

1. **学习提升主要由"反馈有没有点出错因"驱动。** 诊断价值 +0.33，区间不含零。
2. **裁判准确率的影响在这个样本量下未测出。** 代价的点估计是 +0.07，区间跨零。不能说"没有代价"：critic 判错的 2 张表上，下游确实是 0/6。只是判错的比例不高（2/14），总体上被稀释了。
3. **warm-gold（贫）不是上界。** 直觉上"完美裁判"应该是天花板，但它输在反馈贫，不输在裁判。真正的上界是 warm-gold+诊断。全自动的 warm-critic 达到了它的 91%（30/33）。

> **小结**：一个会判错的 LLM 判官可以驱动学习闭环，而且比"只告诉你对错的完美判官"效果好。前提是它把诊断写出来，并且这段诊断进了蒸馏。

## 5. 边界与威胁有效性

读结论之前请先读这一节。

**样本量**

- **实验二的有效样本量约为 14 张表，不是 168 次运行。** cold 完全确定（每轮打印同一个错值），warm 臂也高度重复。3 轮不是 3 个独立样本，所以配对单位取的是表。
- **裁判噪声代价基本靠 2 张表撑着。** critic 只有 14 个独立判定，错了 2 个。"2/14"本身的区间就很宽，由它推出的代价估计不稳。
- InfiAgent 上召回的分母是 18，留出测试是 28 和 18。所有区间都在表里给出，不要只看点估计。

**混淆项**

- **诊断价值里混着信息差。** critic 能看数据画像，蒸馏器看不到。"+0.33"量的是"带数据信息的诊断"相对"只有正确值"的差，不纯是"措辞更具体"的差。如果让蒸馏器自己看数据，这个差可能缩小。
- **critic 的输入里有数据画像**（每列的类型、取值范围、不可解析样例、重复行数等统计）。在注入的坑上，画像可能恰好把问题摆在了 critic 面前。留出测试里没见过的污染缓解了这个担心，但没有消除。
- **agent 模型在各实验间不同**（留出测试是 qwen3.8-27b，其余是 qwen3.8-2.4t-a95b，其中 4 题未限思考）。各实验内部一致，跨实验的数字不宜直接比较。

**数据**

- 实验二的坑是**注入**的 7 种 × 2 张表，不是自然出现的。表是真实的，脏是我放的。
- 准入要求"cold 必错"，所以 cold = 0/42 是筛选的结果，不是发现。提升的绝对值因此偏乐观；臂与臂之间的对比不受影响。
- InfiAgent 只用了"单数值答案"子集（95/257 题）。筛选按的是标签条数，da0039 说明有的题实际要求多个答案、标签只给了一个。
- InfiAgent 的数值匹配规则（|差| < 1e-6）是按基准的说明实现的，没有逐行对照官方评测代码。

**执行循环**

- agent 是"盲写一份脚本，失败才重试"，不是每步都能看输出的 ReAct。这与上一轮消融和 InfiAgent 的跑法一致，四臂之间公平。但 4.6 的失败模式很大程度上是这个循环造成的，换一种循环，各臂的绝对水平和坑的难度排序都可能变。

**人工判断**

- 3.4 的第二个口径是事后人工改标，且只查了被 critic 标记的运行。
- 4.6 的失败分类是关键词匹配。
- 同分布测量里发现过一条 gold 假通过（答案行错了，但末尾另一行的数字恰好等于 gold），已在数据里改标并保留原标签。

## 6. 结论与下一步

### 6.1 分层验证器的定位

- **L0 启发式**：管崩溃。对静默错误无效，这是结构性的。
- **L1 静态探针 / L1b 变形复跑**：零 token，适合当"已知错误类型的回归测试"。不泛化，在合法数据上会误报，不能单独当闸门。
- **L2 critic**：唯一在没见过的错误和真实数据上都有实质表现的一层。代价是每次几千 token，以及一个保守倾向：题意有歧义时它看见了问题也会放行。

### 6.2 LLM 验证器 = 闸门 + 反馈生成器

做实验之前，我把 critic 只当成闸门：判对错，越准越好。实验二说明它还有第二个身份。

同一次 critic 调用产出两样东西：一个判定，一段诊断。在学习闭环里，诊断带来的提升（+0.33）远大于判定不准带来的损失（+0.07，未测出）。这改变了该优化什么：与其追求判官更准，不如先保证它的诊断被完整地传给下游。

反过来，critic 的失败模式也因此更具体了：最伤的不是漏判本身，而是漏判之后蒸出一张"成功经验"卡，把错误做法固化下来。

### 6.3 下一步

1. **成功记忆与强→弱迁移。** 目前种子全是失败运行（cold 0/42），没测过"从成功里学"。另一个方向是强模型蒸卡、弱模型使用。
2. **执行层。** 4.6 最大的失败类别是"看见了但没法改"。让 agent 在成功执行后也能看输出再决定，或者把 critic 接进运行内触发重试，是直接针对它的改动。这要动 runtime，本轮没有做。
3. **跨领域。** 现在只有表格聚合一种任务。BIRD（text-to-SQL）上有现成的执行结果 gold，可以检验这些结论是否只在 pandas 脚本上成立。
4. **补样本量。** 裁判噪声代价需要更多独立的 critic 判定才能测出来，也就是更多的表，而不是更多的轮次。
